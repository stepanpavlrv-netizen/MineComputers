# Песочница для страниц-программ на хостинге

## Зачем

На хостинге (`/sites/<имя>` на сервере, программа `httpd`) страницы клиентов `*.lua` сейчас выполняются прямо внутри
процесса `httpd` с окружением `__index = _G`: видят весь диск сервера, могут выключить его, убить процессы, слать
сообщения от его имени. Бесконечный цикл в странице подвешивает все сайты сервера. Нужна изоляция, при которой
игроки могут делать **любые сайты** (так сказал автор), но не могут навредить серверу и другим клиентам.

## Цели

- Страница клиента выполняется в **отдельном процессе** (`LuaMachine`, своё ядро) с ограничениями, которые проверяет
  Java, а не Lua.
- Видит как свой диск только папку своего сайта (+ `/rom` только для чтения, чтобы работали библиотеки).
- Может читать/писать файлы своего сайта (гостевые книги, счётчики, базы), ходить на другие сайты (`http.get`),
  отправлять письма (порт 25).
- Ограничение времени и памяти; зависшая/тяжёлая страница убивается, остальные сайты работают.
- Не больше 2 страниц одного сайта одновременно; при нехватке ядер — ответ «сервер занят», а не зависание.

## Не цели

- Песочница для `/www` владельца сервера: это его собственный код, остаётся как есть (решение Claude, можно поменять).
- Квоты диска для клиентов, срок работы сайта — следующая работа (пункт 2 очереди).
- Подписи/проверка подлинности писем — тема «взлома» (пункт 6).

## Анти-цели (провал, даже если «работает»)

- Страница может выйти из своей папки (`..`, абсолютные пути, ссылки через `/rom` и т. п.).
- Страница может слушать порты сервера (80, 25, 22, 2121…) и перехватывать чужие запросы.
- Страница может обращаться к сервисам управления на других машинах от имени сервера (ssh 22, хостинг 2121).
- Старые сайты на хостинге перестают работать (обычные `.page` и простые `.lua` с `request`/`echo`).

## Подходы

- **А. Урезанное окружение Lua внутри `httpd`.** Мало работы, но дырявое: общие таблицы (`string` через метатаблицу
  строк и т. п.) позволяют испортить сам `httpd`; бесконечный цикл всё равно вешает сайт.
- **Б. Отдельный процесс с ограничениями в Java (выбран автором).** `computer.spawn` уже создаёт отдельную Lua-машину
  на своём ядре; добавляем ей «клетку». Обойти из Lua нельзя, есть лимит времени и памяти. Цена: больше работы,
  страница открывается чуть медленнее (запуск процесса).
- В. Отдельный компьютер/машина на каждый запрос — избыточно, то же Б, но тяжелее.

## Как устроено (решения)

### Клетка процесса (Java)

- В `LuaMachine` — необязательное поле «клетка» (`Jail`): корень (например `/sites/shop.mine`) и признак ограничений.
  Задаётся только при запуске через новый вызов (ниже); обычный `computer.spawn` без изменений. Процессы, запущенные
  из клетки, наследуют клетку (лучше — вообще запретить `spawn` в клетке; решение Claude: запретить).
- `fs` в клетке: путь страницы `p` → `корень .. normalize("/" .. p)`; `normalize` уже убирает `..`. Исключение — `/rom`
  (только чтение, реальный `/rom`). Всё, что вне корня после нормализации, — «Нет такого файла». `fs.list("/")`
  показывает содержимое папки сайта (+ `rom`). Сообщения об ошибках не раскрывают реальный путь `/sites/...`.
- `os`: время, таймеры, события, `os.sleep` — да; `shutdown`/`reboot`/`setLabel` — ошибка «Недоступно на хостинге».
- `computer`: только безобидное (время, `pullEvent` и т. п.); нет `spawn`, `kill`, списка процессов, сведений о железе
  (решение Claude: можно вернуть часть, если окажется нужно).
- `net`:
  - `open(port)` — только порты 40000–49999 (так их и выбирают `http.get` и почта);
  - `send(target, port, …)` — только на порты 80 и 25; `reply` HTTP — да;
  - `close(port)` — только портов, которые открыла сама страница (иначе закрыла бы порт 80 серверу);
  - `dns`, `address`, `hostname`, `speed` — да; управление Wi-Fi/адаптером — нет.
- **События:** сейчас `net_message` рассылается всем процессам компьютера (`Computer.netReceive`), а `queueAll` —
  всем. Процесс в клетке получает только `timer` и `net_message` на **свои** порты — иначе страница слышала бы
  чужие запросы (с паролями из форм), письма и загрузки на хостинг.
- Нет: `auth`, `bios`, `switch`, `camera`, `sound`, `term` (страницу никто не видит; `term` — заглушка или nil),
  `gpu`. Есть: `string`, `table`, `math`, `bit32`, `unicode`, `data` (хеши, шифрование), `os.time` и т. п.
- Лимиты: память — меньше обычного процесса (например 512 КБ); время — 5 с реального времени на ответ (константы в
  одном месте). По истечении процесс убивается.

### Запуск страницы

- Новый вызов, доступный только вне клетки, например `computer.spawnPage(корень, файл, request)` → pid.
- Внутри процесса BIOS вместо `_PROCESS` видит `_PAGE`: загружает файл с окружением, где есть `request` и `echo`
  (как сейчас), выполняет, результат — строка (`return` или накопленное `echo`).
- Результат возвращается родителю в событии `process_exit` (pid, ok, error, **результат**) — добавить 4-й аргумент.
  Ограничить размер ответа (например 64 КБ; больше — обрезать с пометкой).

### httpd

- Для сайтов из `/sites/*`: `.lua` → `spawnPage`, ждать `process_exit` с этим pid (не дольше лимита + запас), остальные
  события не терять (`httpd` и так однопоточный цикл; на время ожидания — копить входящие запросы в очередь, решение:
  обрабатывать запросы по одному, как сейчас, но страница больше не может подвесить сервер дольше лимита).
- Счётчик активных страниц на сайт; больше 2 или нет свободного процесса → `503`, страница «Сервер занят, попробуйте
  позже».
- Тайм-аут → `504` «Страница слишком долго отвечала». Ошибка в странице → `500` как сейчас (без реальных путей).
- `/www` — как сейчас.

### Совместимость

- Старые `.lua`-страницы, использующие `request`, `echo`, `return "текст"`, `http.get`, файлы своей папки, —
  работают без изменений.

## Проверка

- `HeadlessTest`: страница пытается прочитать `/etc/...` сервера и чужой `/sites/other` → нет доступа; `..` → нет;
  `os.shutdown` → ошибка, сервер жив; `while true do end` → 504 и следующий запрос к другому сайту отвечает;
  гостевая книга пишет в свой файл и читает его; `http.get` на другой сайт из страницы — работает; `net.open(80)`
  и `net.send(x, 22, …)` → ошибка.
- `./gradlew build`, игровые тесты, зелёный CI.
- README: раздел про хостинг — что могут страницы клиентов и чего не могут.

## Оставлено исполнителю

- Точные значения лимитов, как именно пробросить клетку в `LuaApis.fs/os/net` (обёртка или проверка в каждой
  функции), формат `_PAGE` в BIOS.

## Известный остаток риска

- Страница может отправить письмо с любым именем отправителя на этом сервере (подделка отправителя). Получатель не
  может это проверить без изменения протокола почты — оставляем как риск и переносим в тему «взлом» (пункт 6).
- Число процессов ограничено железом сервера (`maxProcesses`): на слабом сервере страниц-программ одновременно
  будет мало, остальным — 503. Это честное ограничение железа, а не ошибка.
